# 活动补充、预算等待和作息让路验证

本轮属于 2026-10-30 三小时完善工作中的自主活动分支。只使用独立合成角色、独立
Windows 桌面和本机响应夹具；不调用真实 API，不读取正式对话，不改变系统时钟、
正式配置、人设或正式存档。构建与部署由主任务统一进行。

## 源码检查结果

1. 原 `ActivityGenerator` 将统一额度预约拒绝返回为 `model_call_budget`。宿主把它
   当成规划失败增加 `planning_cadence.failures`，即使根本没有发出模型请求，也会
   拉长后续退避。额度恢复没有对应的可调用边沿，只能继续等先前退避。
2. 原睡眠分支取消生成后直接返回，没有记录本进程曾因睡眠暂停规划。醒后可能
   继续沿用睡前较长的安静退避。应用结果时也没有显式检查实际睡眠状态。
3. 作息插件只在活动队列为空时接纳睡眠请求。持续补充可以使活动队列始终非空。
   是否实际发生以及候选修复的效果，需分别保留旧宿主和候选宿主的进程证据。

## 首阶段实现

`src/ActivityRuntime.inc` 在需要补充时先检查每日后台额度和每小时前台保留额度，
等待期间最多每秒检查一次；真正调用前仍经原 `reserveCall` 原子预约。没有降低
前台保留量，也不清零已经使用的调用数或 token 数。模拟模型不消耗实际调用额度，
不因这个预检查停止免费模拟。

额度从等待变为可用时，重新检查活动补充时机。等待仍受用户输入、当前任务、实际
队列容量及语音状态约束。审核阶段抢不到最后一个预约的竞争也归为预算等待，不能
伪写成模型拒绝或协议失败；已经使用的角色调用照常计数。

实际睡眠时取消并失效尚未应用的规划批次。实际醒来后重新考虑，旧的安静／失败
退避不充当新的醒后选择；真正的新选择仍可以为空。此处不更改睡眠惯性、情绪、
角色设定或唤醒概率，也不把“准备重新规划”写成活动已经完成。

`planning_deferred_reason` 是管理状态元数据，可为 `hourly_reserve`、`daily_calls`、
`daily_input_tokens`、预约竞争的 `model_budget` 或实际 `circadian_sleep`。空值不等于
保证能调用；统一预约和现场检查仍可能在下一步拒绝。

## 专项测试入口

`tests/ActivityRecoveryFixture.cpp` 只接受带有精确合成标记的新目录，拒绝已有档案或
已有密钥。它通过真实 vault codec 建立预算和规划时钟种子，不访问生产数据。

`tests/ActivityRecovery.ps1` 接受 `ProjectRoot`、`BuildRoot`、`SeedExecutable` 和独立
`ScratchRoot`。`-ObserveOnly` 为旧宿主保存差异，不把缺少修复伪装为通过。

- `hourly`：真实等待合成小时额度到期，检查等待没有付费请求或失败退避，恢复后
  是否自动补充。没有修改电脑时钟。
- `review-budget`：角色用掉最后一次后台预约，审核被门控；随后明确提高合成额度，
  检查恢复后真实角色／审核调用数和已有用量。
- `wake`：先持有长安静退避，使用真实作息配置、姿态确认与唤醒回执，再检查新考虑。
- `balance`：本机余额端点从无余额变为有余额，确认自动离线解除不会覆盖手动离线，
  操作者恢复后实际补充继续且额度账本保留。
- `starvation`：连续返回四项各十秒的有限等待，三十秒补充间隔；在队列运行时配置
  当前休息窗口，连续五十秒保存实际 phase、活动队列、当前活动和模型请求数。

所有结论以相应独立目录中的 `acceptance.json` 和实际进程结果为准。尚未运行的
场景不能视作通过；不同构建的观察不能混算成同一版本的运行时长。

## 动作目录与素材边界

本轮不增加动作 ID、不新增姿态、素材或 PixelLab 提示词。REST-01～03、S01／S07
的起止姿态和单次／循环关系保持原样。对 REST-06／07 的同步仅涉及活动补充的等待、
失效和重新考虑；进入睡眠仍必须由实际姿态确认。

已有队列最多六项，等待／姿态至多 120 秒、短休至多 600 秒；待执行项有原十分钟
期限，实际动作仍以真实回执或原 deadline 结束。异步插件若违背自身超时约定，
当前宿主不能安全强杀同进程线程，因此不能声称所有插件都有无条件的硬时间上界。
前台任务和用户操作不应被作息让路策略强制取消。

## 旧版复现与候选接线

旧 0.8.0 宿主的独立 `starvation -ObserveOnly` 已完成。窗口配置后采集 83 个样本，
首末跨度 49.931 秒，phase 始终为 `idle`；真实角色请求从 1 增至 2，末尾仍有 3 个
待执行项及 1 个实际执行项，没有进入睡眠。证据在
`E:/Aliyat/Validation/ActivityRecovery/baseline/20261030-120219-7396253bfb1449db95c907865775644d/acceptance.json`。
这证明持续补充在该具体负载下确实阻挡了作息接纳，不声称已经观测任意长时间。

获批准的第二阶段仅增加 `Rhythm.snapshot` 的 host 调度位
`circadian_admission_ready`，复用原 `mayStart` 的当地时段、冷却及同一时段判定，
不会进入 `rhythm.observe` 或角色上下文。宿主在此位或实际 queued/requesting/sleeping
阶段停止新的后台补充及峰值复用，丢弃未应用的在途补充结果；已批准的有限活动仍按
原规则顺序完成或过期。`activityPending` 门控保留，不提前伪写睡眠，也不取消前台。
候选是否实际改善，以新的 `starvation` 进程证据为准。

首轮候选回归的审核预算场景曾失败。只读认证检查显示第一次确实为
`model_call_budget / deferred_budget`，第二次为 `activity_review_format / model_rejected`，
预算实际使用 3、失败 1、安静 0。原因是新测试的 approve 夹具误用了
`reason=synthetic`，而现有协议要求 `reason=ok`。已更正夹具，未放宽产品验证或断言。
原失败保留，诊断在 `E:/Aliyat/Validation/ActivityRecovery/diagnostics/phase1-review-format.json`；
这不能被改称为原场景已经通过。

统一候选的专项进程测试已通过 28 项检查，实际耗时 176.83 秒；五个场景均执行，
没有真实模型调用。证据为
`E:/Aliyat/Backups/HibernationAgent/optimization-3h-20261030/build/integration/activity-recovery/20261030-122402-9f43864879a2410da8d54e89024cabd8/acceptance.json`。

审核预约恢复后 334 毫秒取得新的已审核安静选择，已有调用用量保留为 3；实际醒来后
285 毫秒取得新的安静选择，旧 quiet=4 不再阻挡；余额恢复和明确联机后 274 毫秒
重新补充。小时保留额度场景真实等待额度到期后恢复，期间没有失败退避。

作息饥饿候选样本 56 个、跨度 42.541 秒。原四项等待自然完成后实际进入 sleeping，

host 调度位未进入模型请求。旧版 49.931 秒观察与此候选是独立证据，不合并运行时长。
