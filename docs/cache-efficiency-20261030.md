# 缓存前缀与实际用量修正（2026-10-30）

本次只处理输入排列和程序统计，不更改人设、审核标准、授权资料范围、默认审核布局或模型连接。没有发送真实外部 API 请求，也没有读取正式档案来构造实验。

## 代码检查所得问题

`ModelCacheRuntime.inc` 原来在累计超过 32 个历史连接或单连接超过 24 种调用用途时直接返回；超过用途限制的请求甚至不再进入连接总计。后台日预算仍可能记录了这些调用，但费用面板会漏计。现在保留原正常桶，并使用固定的 `$other_profiles` 与 `$other_purposes` 合并其余请求。连接最多 32+1 个，每个用途最多 24+1 个，不追加被省略 ID 的名单；所有后续已报告数值继续进入总计；此前已漏掉的派生统计不会凭空回填，供应商账单仍是费用依据。溢出连接标记 `aggregation=additional_profiles`，不能被解释为某一个具体模型。

`usage_reported_calls` 原来表示输入或输出任意一项存在，不能证明两项均存在。新增字段如下：

|字段|含义|
|---|---|
|`input_tokens_known` / `output_tokens_known`|该累计中至少存在一份真实的对应报告，含服务商明确报告的 0；并不表示所有请求都完整报告。|
|`input_reported_calls` / `output_reported_calls`|该项确实已报告的调用数。|
|`complete_usage_reported_calls`|输入、输出同时报告的调用数。|

旧累计没有保存分项次数，无法从原总和重建：这些新次数保持 `null`，不填成 0 或推测历史调用都完整。历史正总量可以证明该项曾报告；历史 0 无法证明，直到新的真实报告出现。原 `usage_reported_calls` 和累计 token 保持兼容。负数、非整数、布尔和缺失值不视作实际 token；整数计数饱和而不回绕，发生饱和时标记 `counter_saturated`。若命中或未命中累计本身饱和，另标记 `cache_counter_saturated` 并将比例保持未知，不用截顶数字给出虚假精确率。

缓存比例仍只使用服务商同时提供命中与未命中的配对样本，不把缺失一侧当成零，也不把本地字节前缀当成服务商命中率。

## 相同资料之前不再放易变事件类型

此前事件 JSON 先写 `event_kind`，相同已授权历史在用户消息与后台事件切换时，开头几十字节便分叉。现在先写交付方式与本次原有的授权历史，再写事件类型及其余现场字段。解码后的 JSON 完全等价，消息长度不增加，未新增、复制或扩大历史；来源撤销时不保留被撤销内容。

这只增加可能复用的相同字节前缀，不保证供应商实际命中率提升。八小时记录中审核与角色的负载、布局及输入量并不相同，不能据已有分路比例声称审核逻辑有错，或为了命中而携带无关资料。

## 验证范围

`CacheContext` 新增用例覆盖跨事件类型的内容等价与首分叉、配对与缺失用量、明确零、旧累计迁移、历史桶溢出及饱和。`ReviewSnapshots` 补充审核包装内相同授权前缀及撤销来源检查。`CacheUsageAccounting.ps1` 使用本地供应商进程，检查输出单项、零用量、缺失报告、无新增调用及重启持久化。

独立局部 C++ 探针在新的 artifacts 目录编译运行，没有写入既有 build 输出。已验证 69 次合成报告全部保留、输入合计 690、连接桶有界；相同 12000 字节资料在事件类型变化后仍保留约 12050 字节共同前缀。完整应用单元及独立进程结果由主代理统一构建后记录，尚未运行的结果不冒充通过。


## 仍保留的重复轮次局限（仅审查，未改行为）

`Application.cpp` 已通过 `failedAttempts` 缓存同参数、非可重试的失败，`OperationReplay` 复用审核改写前已成功的操作回执，媒体能力另有实际执行次数上限。`CallBudget.ps1` 覆盖格式修复不吃工具轮次及预算核对；`NativeTools.ps1` 与单元测试覆盖审核改写不重做副作用；`ProtocolIntegration.ps1` 则明确构造五次相同失败的 `television.open` 提案，再取得最终对白。程序不会执行五次相同失败操作，但模型仍可生成多轮相同提案，启用相应语义审核时还可能增加审核请求。副作用去重不能等同于省掉了这些模型调用。

候选策略是统计整批都只领到 `deduplicated` 且非 `retryable` 失败回执的停滞，若连续达到阈值，则复用现有最终阶段规则，让下一次只能给出 reply 或 silence；新回执、可重试失败、成功操作的审核重放不应计作停滞。它也可能过早阻止模型在旧失败后改换参数恢复，因此本轮没有增加默认截断、没有减少审核标准，也不声称上述局限已经修复。应另行确定阈值或显式选项，并用失败后换参数成功、混合批次和审核改写场景做对照。


## 候选进程回归补充

统一候选初次相关回归中，`CachePipeline.ps1` 仍硬编码要求审核内层 JSON 以 `event_kind` 开头，因此失败；原 `phase1-related-regression.log` 与失败夹具保留，没有覆盖。检查实际夹具确认：新排列把授权源放在事件类型前，事件类型仍为真实 `user_message`，事件 ID 与角色请求一致，授权源的完整数据、版本与身份语义相同。

测试改成三项独立检查：共享授权前缀在变化的事件类型前；实际事件类型与 ID 保留；受控夹具中的全部授权源以 JSON 语义深比较相等。随后用统一的候选程序独立复跑，15 项进程检查通过。新日志为本轮 `cache-pipeline-fixed.log`，证据目录为 `process-checks/cache-0890614a296840b09ec4a9341e4f4334`。这修正的是过时的排列断言，不是删除内容或来源检查；没有为修复测试改产品行为。
