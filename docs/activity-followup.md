# 桌面动作后的约定接续（0.9.2）

“我尝一口再告诉你”需要真实动作和可追踪的后续约定，单靠对白不会执行。
本功能复用已有加密记录、`ha.schedules`、DurableQueue、审核、后台预算及桌面回复／语音
通道；没有额外轮询模型或另建事件系统。

## 模型入口

桌面会话的 `activity.enqueue` 可附加：

```json
{
  "commands": [{"kind":"eat_nearest"}],
  "follow_up": {
    "topic":"尝过后接着回答刚才那份食物的问题",
    "timeout_seconds":60
  }
}
```

这里只是结构示例，不是固定台词或吃过的事实。参数限定为 `topic` 和 5–600 秒的等待
上限；必须有真正接受的活动。普通动作和意向不强制安排后续。明确承诺稍后反馈时，
角色及审核器会检查实际登记回执；`follow_up.registered=true` 才表示接续已排入调度。
同一事务保存活动队列、受来源限制的后续记录和动作绑定，避免只有对白或只有动作。
回执同时返回实际 `activity_ids`。登记失败不谎称成功，也不自动重做已经执行的操作。

该入口当前仅供直接桌面对话／小组件输入使用。QQ、Skill 和持续任务不能借它跳出
原有会话或权限范围；原有 `activity.enqueue` 不带此字段时保持兼容。没有读取本次
不可访问的历史、修改核心人设或自动生成角色已尝过的感受。

## 生命周期

- 每个绑定动作在完成、失败、取消、尚未开始就取消或重启中断时，保存有来源的实际
  终止回执。仅对已登记后续的动作保存这份专用回执，不给所有日常动画无限复制记录。
- 通过明确结果检查，而非估算动画时长或反复询问模型。当本批动作全部终止，调度器
  提前给角色一次独处接续机会；等待上限到了但仍缺少确认时，明确标为 `not_confirmed`。
- 来源仍须可访问。撤权会阻止接续，不能通过之前的约定继续保留受限内容。模型收到
  原问题、约定目的和实际结果；原先打算与已发生事实分开，不能据排队或超时编造味道。
- 明确约定使用确定性唤醒，不走普通记忆的随机回想。实际接续仍可简短回复、拒绝，
  或在后来对话已处理等情况下保持安静；不会为了显得活跃强制发言。
- 暂停／离线／作息继续适用。后台预算不足不删除约定、不清零用量；恢复可用额度后
  自动重新安排。其他调用失败最多三轮有限重试，仍失败则保留终止状态和记录。
- 等待保留两天，覆盖日预算恢复；超期停止自动接续，历史保留。不是无限承诺队列。
  最多四项同时等待，复用四个有单调执行编号的调度槽位，避免每次完成都占用新槽位。
  热索引达到上限时只收缩较旧的已终止后续项，原始约定、结果及历史版本仍保存在数据库。
  沿用总计划数和任务槽位上限。既有 `schedule.cancel` 可取消，
  不能通过普通 `schedule.update` 偷换已绑定动作。
- 正常回复与小组件／语音沿用已有投影及已展示标记，重启不重复投递已完成的回话。
  短动作回报跳过无关长档压缩，减少接续前额外调用。

`GET /api/followups` 只给管理诊断返回 ID、状态、时间及重试信息，不包含话题、对话、
记忆、来源正文或工具结果。`answered/silent/deferred_budget/delivery_failed` 与调度
任务状态分开，能够区分没有唤醒、等待额度、模型已选择安静和实际回复。

## 检查

`tests/ActivityFollowup.ps1` 使用独立合成人设、本地模拟供应商和非活动桌面，检查只发
一次用户消息后能自动回应，并覆盖取消、超时、重启、日预算阻止与恢复、去重和诊断
无正文。普通定时计划、前台优先级、活动反思、原生工具及旧活动队列另做回归。
这些流程通过不代表真实模型每次都会选择登记，也不能证明拥有实际味觉；真实说法
仍受角色选择和可观察的虚拟食物属性限制。
